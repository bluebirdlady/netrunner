Corp AI Evaluation: Reasonable but Suboptimal

From the logs, the Corp AI makes generally acceptable choices, but several recurring suboptimal patterns suggest room for improvement. Below is a breakdown of observed decisions.
✅ Reasonable Behaviors
Situation	AI Action	Why It’s Reasonable
Rezzing ice	Rezzes Tithe (cost 1), Whitespace (cost 2), Palisade (cost 3), Karunā (cost 4), Pharos (cost 7) when runner can break them	AI uses a heuristic: “runner can trivially break → consider bluff; if cheap enough, rez anyway.” This prevents free passes.
Bluff recognition	“runner can trivially break X — considering bluff” – but still rezzes cheap ice.	For very cheap ice (≤3cr), rezzing is low risk; runner still pays break costs.
Install order	Places ice on servers before assets (e.g., Palisade in front of R&D, Whitespace + Tithe in HQ)	Mimics basic defensive layering.
Hedge Fund usage	Plays Hedge Fund early to build credits, sometimes twice in a row.	Standard Corp economy play.
Agenda advancement	Advances Superconducting Hub to 3 counters before scoring.	Correct – no over‑advance waste.
Retribution play	Plays Retribution when runner is not tagged (condition fails, no effect).	AI doesn’t check condition before playing? Actually it plays anyway – condition is evaluated inside the ability, so the card is still played but fizzles. This wastes a click and the card.
❌ Suboptimal Patterns
1. Rezzing ice that runner can easily break – even when expensive

    Example (Game 1, turn 15): Karunā (cost 4) rezzed against runner with Carmen (strength 5, breaks for 1cr per sub). Runner breaks both subs for 2cr total. Corp wasted 4cr.

    Example (Game 3, turn 4): Pharos (cost 7) rezzed; runner breaks both subs with Cleaver for ~2cr. Corp lost 7cr for nothing.

    Better: AI should compare break cost (estimated from runner’s board) vs rez cost. If break cost < rez cost, maybe don’t rez unless it’s a critical server.

2. Failing to protect centrals later in the game

    Game 1, turn 24: R&D has only Palisade (position 0) and an unrezzed Diviner (position 1). Runner breaks Palisade, passes Diviner (unrezzed), accesses R&D and steals a 3‑point agenda to win.

    Issue: Diviner was installed but left unrezzed when it could have ended the run or done damage. AI had 24+ credits at that point – could afford to rez.

    Better: When runner is approaching a central with game‑point agendas, rez all ice if affordable.

3. Wasting clicks on Hedge Fund when already rich

    Game 3, turn 1: Reality Plus plays Hedge Fund twice, going from 5 → 14 → 23 credits. No ice installed on R&D or HQ until much later.

    Issue: Over‑economy without defense. Runner steals a 2‑point agenda from unprotected R&D on turn 4.

    Better: Prioritise installing at least one piece of ice on centrals before second Hedge Fund.

4. Not recognising “must run a central first” restriction

    As Corp, Replicating Perfection enforces the restriction correctly. But the Corp AI doesn’t exploit it – it never installs additional ice on centrals after seeing the runner repeatedly fail remote runs. The runner eventually runs Archives (central) and wins.

    Better: When playing an ID with central‑only restriction, Corp AI should reinforce centrals (more ice, upgrades) because the runner has to run them eventually.

5. Playing Retribution when condition will fail

    Happens twice in Game 3 (turn 3 and turn 4? Actually turn 3 Retribution, turn 4? Wait – Game 3 turn 3: “Condition not met — ability has no effect.” Then Reality Plus plays Retribution anyway.)

    Issue: AI doesn’t pre‑check the condition (runner_is_tagged). It wastes a click and the card.

    Better: In choose_action(), evaluate playable operations against their conditions. If condition fails, don’t offer/play that operation.

6. Not using upgrades or paid abilities

    Game 1: Replicating Perfection never activates Spin Doctor (Archives shuffle), Malapert Data Vault (peek R&D), or Urtica Cipher (pay 2cr for net damage) – all were installed or in HQ.

    Better: Corp AI should have a list of high‑value paid abilities and trigger them when beneficial.

📊 Overall Assessment
Aspect	Grade	Notes
Basic economy	B+	Plays Hedge Fund, gains credits, but sometimes over‑accumulates.
Ice rezzing	C+	Rezzes too aggressively against breakers, wastes credits.
Defensive positioning	C-	Leaves centrals under‑protected; fails to rez ice when it matters.
Ability usage	D+	Rarely uses card‑specific paid abilities or conditional triggers.
Condition awareness	D	Plays Retribution when runner isn’t tagged; doesn’t pre‑check.
Win condition prioritisation	C	Doesn’t defend game‑point agendas; allows runner to steal winning agendas too easily.

Final verdict: The Corp AI is functional for casual play but predictable and suboptimal against a competent runner. It will lose most games where the runner builds a decent rig and runs centrals repeatedly. To be competitive, the AI needs:

    A break‑cost estimator for rez decisions.

    Condition pre‑checking before playing operations.

    Central server reinforcement when playing Replicating Perfection or against a runner focusing centrals.

    A priority system for paid abilities (e.g., always use Malapert Data Vault if available).

Work Plan: Refactoring AbilityInterpreter.gd

This plan breaks the monolithic script into maintainable, testable modules. Each step is backwards‑compatible – you can commit after each step without breaking existing cards.
Phase 0: Preparation

    Back up the current file (git branch refactor/ability-interpreter).

    Write integration tests for 5–10 representative cards (e.g., one damage, one counter, one run effect) using the existing GameContext mock.

    Add randomize() to the game startup (outside the interpreter).

Phase 1: Extract Helpers & Reduce Duplication

Goal: Remove repetitive code inside _execute_effect without changing external behaviour.
Step 1.1 – Self‑card getter
gdscript

# At top of AbilityInterpreter (private helper)
func _get_self_card(ctx: GameContext) -> InstalledCard:
    var iid = ctx.current_event_data.get("card_instance_id", "")
    if iid.is_empty():
        return null
    var card = ctx.get_installed_card_by_instance_id(iid)
    if card == null:
        card = ctx.get_installed_card_by_id(iid)
    return card

Replace all occurrences of the 5‑line lookup pattern with _get_self_card(ctx).
Step 1.2 – Unify “optional ability” prompt

Create a helper:
gdscript

func _ask_optional(prompt: String, ctx: GameContext, player: String = "active") -> bool:
    var dm = ctx.corp_decision_maker if player == "corp" else ctx.runner_decision_maker
    if dm and dm.has_method("choose_optional_ability"):
        return await dm.choose_optional_ability(prompt, ctx)
    return true   # AI default

Use it for idiosyncresis_activate, mitra_aman_approach, zwicky_optional_draw, etc.
Step 1.3 – Consolidate install logic

Create _install_card(record: CardRecord, server: Server, zone: String, rezzed: bool, ctx: GameContext) -> InstalledCard.
Then rewrite install_ice_from_hq, install_any_from_hq, install_from_archives_free, etc. to use it.

Checkpoint: Run integration tests – all should pass.
Phase 2: Split Effect Handlers into a Registry

Goal: Break _execute_effect (1800+ lines) into separate handler functions.
Step 2.1 – Define handler interface

Create a new file effect_handlers.gd (or a folder effects/). Each handler is a static function:
gdscript

static func handle_gain_credits(effect: Dictionary, ctx: GameContext, target: Variant) -> void:
    var params = effect.get("params", {})
    var subject = params.get("subject", "corp")
    var amount = params.get("amount", 0)
    ctx.set_credits(subject, ctx.get_credits(subject) + amount)
    ctx.send_log(...)

Step 2.2 – Build a dictionary mapping type → handler

In AbilityInterpreter:
gdscript

const _handlers = {
    "gain_credits": _handle_gain_credits,
    "lose_credits": _handle_lose_credits,
    # ... all 70+ types
}

Keep the handler functions inside the same class (as static or instance methods) for now.
Step 2.3 – Rewrite _execute_effect
gdscript

func _execute_effect(effect: Dictionary, ctx: GameContext, chosen_target: Variant) -> void:
    if effect.has("condition") and not _evaluate_condition(effect["condition"], ctx):
        return
    var etype = effect.get("type", "")
    var handler = _handlers.get(etype)
    if handler:
        await handler.call(effect, ctx, chosen_target)
    else:
        push_error("Unknown effect type: ", etype)

Step 2.4 – Extract one handler at a time

Start with 5 simple effects (e.g., gain_credits, draw_cards, give_tags). After each, run tests. This is safe and incremental.

Checkpoint: All effect types moved to individual functions; _execute_effect becomes ~20 lines.
Phase 3: Extract Condition Evaluation

Goal: Move condition logic to a separate class for reuse and testing.

    Create ConditionEvaluator.gd (extends RefCounted).

    Move _evaluate_condition and its helper _resolve_amount into it.

    Pass GameContext and current_event_data explicitly (or keep as part of ctx).

    Replace all internal calls with ConditionEvaluator.new().evaluate(...).

    (Optional) Inline the few places that still use _evaluate_condition in effect handlers – they now use the new evaluator.

Phase 4: Refactor Target Resolution

    Extract TargetResolver.gd with a method resolve(target_spec, ctx).

    Move _resolve_target logic there.

    For random selection, inject an RNG instance (to make tests deterministic).

Phase 5: Isolate Encounter Actions

The process_encounter_action and its helpers (_do_boost, _do_break_sub, etc.) are tightly coupled to EncounterState.

    Create EncounterProcessor.gd.

    Move all encounter‑related methods into it.

    Pass encounter, ctx, and ability_registry as arguments.

    Keep _find_breaker as a private static helper inside the new class.

Benefit: AbilityInterpreter no longer knows about icebreakers or subroutines.
Phase 6: Introduce Typed GameContext

Goal: Replace dynamic ctx property access with a real GDScript class.
Step 6.1 – Create GameContext.gd (extends RefCounted)

Declare all fields:
gdscript

var runner_tags: int = 0
var corp_credits: int = 5
var runner_credits: int = 5
var runner_hand: Array   # of Dictionary {card_id, card_record}
var corp_hand: Array
# ... (all existing dynamic fields)

Step 6.2 – Move helper methods

    get_credits(subject), set_credits(...)

    runner_is_tagged(), threat_level()

    get_installed_card_by_instance_id(iid)

    notify_event(...) etc.

Step 6.3 – Update the interpreter

Change all ctx.runner_tags to ctx.runner_tags (still works because it’s a property now, not a dynamic key).
Remove any ctx.set_meta / ctx.get_meta – replace with dedicated fields (e.g., ctx.current_event_data as a Dictionary, ctx.run_modifiers as Dictionary).

Checkpoint: The interpreter now uses a strongly‑typed context – compile errors will catch typos.
Phase 7: Remove Hard‑Coded Card IDs

Goal: Move special‑case logic into JSON abilities where possible.

    For au_co_the_gold_standard_in_clones: create a new effect type "au_co_place_power_counter" and move the logic there.

    For beta_build_installed_card_id: add a field ctx.beta_build_installed instead of a magic string.

    For "run_event_active": define a constant in GameContext (RUN_EVENT_ACTIVE).

    For card‑specific identity checks (ctx.corp_identity.id == ...): either move the check into a condition in the JSON (e.g., "type": "identity_is", "params": {"id": "au_co"}) or keep as a one‑off but document it.

Rule of thumb: If a card’s name appears in the interpreter, it’s a refactoring target.
Phase 8: Performance & Error Handling

    Replace linear searches with dictionaries:

        ctx.runner_rig_by_instance_id (updated on install/trash).

        encounter.available_breakers_by_id.

    Add early returns after push_error where missing data should abort the effect.

    Wrap all await calls in _execute_effect handlers with error catching (optional, but helps with debugging).

Phase 9: Final Cleanup & Documentation

    Remove dead code and unused variables.

    Write a short README_ABILITY_INTERPRETER.md explaining how to add a new effect type:
    md

    1. Add a new entry in _handlers dictionary.
    2. Create a handler function.
    3. (Optional) Add a new condition if needed.

    Run all integration tests; fix any regressions.

Recommended Order for Minimal Risk:

    Phase 0 (tests)

    Phase 1 (helpers)

    Phase 6 (typed GameContext) – big but pays off early

    Phase 2 (effect registry) – now much easier with typed ctx

    Phase 3 + 4 (conditions & targets)

    Phase 5 (encounter)

    Phase 7 (hard‑coded IDs)

    Phase 8 (performance/errors)

    Phase 9 (cleanup)

Each phase produces a working, shippable interpreter. Roll back if a phase breaks more than 3 tests.
