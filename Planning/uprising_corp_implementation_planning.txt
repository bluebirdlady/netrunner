1A. TRACE MECHANIC (NEW — biggest single piece of work in this set)
─────────────────────────────────────────────────────────────────────────────
Used by: winchester (Trace[4], Trace[3], Trace[3]), scapenet (Trace[7])

Trace is not implemented anywhere in the engine yet. This is the Corp's most
common interactive subroutine type in the broader card pool, so the
implementation should be general enough to cover future sets, not just these
two cards.

Rules summary: Corp reveals a trace strength X (the printed/modified base
value for this trace). Runner secretly (or, in this single-player engine,
via decision-maker) decides how many credits to spend to boost their link
(link + credits spent = Runner's trace strength). Corp may then spend
credits to boost X. Trace succeeds if Corp's final strength > Runner's final
strength (some cards use >=, but standard Netrunner trace is "Corp strength
exceeds Runner strength" — i.e., succeeds on X > link+spent). Both players'
credit spends happen in a single simultaneous-ish step; in this engine we can
sequence it as: Corp may boost first (spend credits to raise X), Runner then
spends credits + link to attempt to meet/beat the (possibly boosted) X.

Changes required:
• AbilityInterpreter: new effect type `trace`
  - params: { "base_strength": int, "on_success": [effects], "on_fail": [effects] (optional) }
  - Step 1: Corp decision — `corp_decision_maker.choose_trace_boost(base_strength, ctx) -> int`
    (amount of credits Corp spends to increase base_strength, 0..corp_credits).
  - Step 2: Runner decision — `runner_decision_maker.choose_trace_link_boost(trace_strength, runner_link, ctx) -> int`
    (credits Runner spends, 0..runner_available_credits).
  - Compute runner_total = runner_link + bonus + runner_link_boost (apply
    any existing link-boost passive modifiers).
  - Trace succeeds if trace_strength > runner_total (Corp's effective
    strength strictly greater than Runner's). Per current rules wording,
    most cards read "Trace[X]. If successful, ..." where success = Corp wins.
  - On success: execute on_success effects. On failure: execute on_fail
    effects (often empty).
  - Both Corp and Runner pay the credits they committed regardless of outcome.
• HumanDecisionMaker: `choose_trace_boost(base, ctx) -> int`,
  `choose_trace_link_boost(strength, link, ctx) -> int` — present a credit
  slider/prompt.
• SimCorpAI / CorpTurnAI: heuristic for `choose_trace_boost` — boost just
  enough to guarantee success against the Runner's known maximum possible
  link+credits if affordable and the on_success effect is high value (e.g.
  Winchester's program/hardware trash, Scapenet's RFG); otherwise boost 0 or
  a small amount.
• SimRunnerAI: heuristic for `choose_trace_link_boost` — spend enough credits
  to beat the (possibly boosted) trace strength if the on_success effect is
  costly (program/hardware trash, chip/virtual RFG) and Runner can afford it
  without going broke; otherwise spend 0.
• GameContext: expose `runner_link` (base link + passive modifiers, e.g.
  Cybertrooper Talut's +1 link from the Uprising Runner side, Mantle, etc.)
  if not already present — check GameContext for an existing `runner_link`
  field before adding a new one.

JSON representation:
  { "type": "trace", "params": {
      "base_strength": 4,
      "on_success": [{ "type": "trash_runner_installed_program", "params": {...} }],
      "on_fail": []
  }}

This is the foundational piece — both Winchester subs and Scapenet's effect
are simple once `trace` exists.

1B. LOCKDOWN MECHANIC (NEW — shared keyword across 5 operations)
─────────────────────────────────────────────────────────────────────────────
Used by: argus_crackdown, hyoubu_precog_manifold, napd_cordon,
         next_activation_command, sync_rerouting

All five share: "Play only if there is no active lockdown. This operation is
not trashed until your next turn begins." While "active," the operation's
ongoing effect applies; it remains face-up in the play area (not Archives)
until the start of Corp's next turn, at which point it is trashed and its
effect ends. Only one lockdown operation can be active at a time (across
both — actually within the Corp's own operations; check Runner side for any
"lockdown" keyword cards too, since the pre_play_condition is "no active
lockdown" globally for the Corp).

Changes required:
• GameContext: new field `active_lockdown_card_id: String = ""` (empty =
  none active). Also store the active lockdown's runtime instance so its
  ongoing effects/listeners can be looked up.
• New pre_play_condition `no_active_lockdown`: true when
  active_lockdown_card_id == "".
• AbilityInterpreter / TurnManager._do_play_corp_operation(): when an
  operation has `is_lockdown: true`:
  - After paying costs and resolving on_play effects, do NOT move the card
    to Archives. Instead set active_lockdown_card_id = this card's id/instance,
    and register its ongoing listeners (e.g. Argus Crackdown's
    successful_run trigger, Sync Rerouting's run_start trigger, Hyoubu's
    successful_run-on-chosen-server trigger, NAPD Cordon's steal-cost
    modifier, Next Activation Command's ice-strength/break-restriction
    passive modifiers).
  - At the start of Corp's next turn (TurnManager._corp_turn() entry), if
    active_lockdown_card_id != "": trash that card (move to Archives, fire
    trash events) and clear the field + unregister its listeners.
• Listener registration: lockdown operations need their `successful_run`,
  `run_start`, passive-modifier, and steal-cost-modifier hooks registered
  the same way rezzed upgrades/assets are (extend
  TurnManager._register_card_listeners() or add a parallel
  `_register_active_lockdown_listeners()` called when a lockdown becomes
  active, and unregistered when it's trashed).

JSON keys: `"is_lockdown": true`, `"pre_play_condition": "no_active_lockdown"`.

1C. RUN-CANNOT-BE-DECLARED-SUCCESSFUL MODIFIER (NEW)
─────────────────────────────────────────────────────────────────────────────
Used by: transport_monopoly

Once per turn, during a run, Corp may spend 1 hosted agenda counter so that
"this run cannot be declared successful." This does not end the run or make
it unsuccessful by itself — it just blocks the run from ever transitioning
to "successful" for the rest of its duration (i.e., Runner cannot breach/
access at the end of this run, but the run also doesn't fail outright —
matches RunStateMachine's existing distinction between "ends in failure" and
"ends without success").

Changes required:
• GameContext / run_modifiers: new flag `run_cannot_be_successful: bool = false`,
  set on the active run's modifier dict. Cleared at run end.
• RunStateMachine: wherever the run transitions to "successful" (i.e., the
  Runner passes the last piece of ice / approaches the server with no more
  ice), check this flag first. If set, the run instead ends in the
  "unsuccessful, no breach" state (Runner does not access anything, and
  effects keyed on `successful_run` do not fire).
• AbilityInterpreter: new effect type `prevent_run_success`
  - params: {} — sets run_modifiers["run_cannot_be_successful"] = true.
  - Only usable `during a run` (gate via existing `run_in_progress` style
    condition — check what condition currently exists for "is a run
    active").
• click_action / hosted-counter ability on Transport Monopoly:
  once_per_turn_key + condition `run_in_progress` + cost: spend 1 hosted
  agenda counter + effect `prevent_run_success`.

1D. APPROACH-SERVER PAY-OR-END-RUN SCALED BY ADVANCED ICE (NEW)
─────────────────────────────────────────────────────────────────────────────
Used by: cayambe_grid

Whenever Runner approaches this server: end the run unless they pay 2cr for
each advanced piece of ice protecting this server.

Changes required:
• AbilityInterpreter: new effect type `end_run_unless_pay_per_advanced_ice`
  - params: { "cost_per_ice": 2 }
  - Count rezzed/installed ice protecting Cayambe Grid's server with
    advancement_counter_count >= 1.
  - total_cost = count * cost_per_ice.
  - If total_cost == 0: no effect.
  - Else: Runner decision `choose_pay_or_end_run(total_cost, ctx) -> bool`
    (reuse existing "pay X or end the run" pattern if one exists — check
    `runner_must_take_tag_or_end_run` / `end_run_if_tagged` for a template
    of the pay-or-end-run dialog).
• Trigger: `approach_server` event with condition `run_target_is_self_server`
  (both already exist from Parhelion/Midnight Sun work).
• Corp turn-begin effect (separate, simple): place 1 adv counter on a piece
  of ice protecting this server — reuse `place_advancement_counter_on_installed`
  with a server-scoped target filter (`server_scoped: true`, restrict
  candidates to ice protecting Cayambe Grid's server).

1E. KONJIN: PSI GAME WITH ICE-ENCOUNTER REDIRECT (NEW psi_game extension)
─────────────────────────────────────────────────────────────────────────────
Used by: konjin

On encounter, psi game; if bids differ, Corp may choose another rezzed ice —
Runner encounters that ice (and when THAT encounter ends, if the run hasn't
ended, the Runner resumes encountering Konjin).

Changes required:
• Existing `psi_game` effect supports `on_mismatch`/`on_match` effect lists.
  Add a new effect type `redirect_encounter_to_chosen_ice`:
  - Corp may choose any other rezzed ice (choose_optional_ability + pick from
    all rezzed ice excluding self).
  - If chosen: push the current ice (Konjin) onto a
    `ctx.encounter_resume_stack` (new field — Array of ice instance ids) and
    begin a new encounter with the chosen ice immediately.
  - If declined: nothing happens, Konjin's own subroutines resolve normally.
• RunStateMachine / EncounterProcessor: after an encounter completes (all
  subs resolved/broken, or ice trashed), check `encounter_resume_stack`. If
  non-empty AND the run hasn't ended, pop the top entry and begin an
  encounter with that ice (resuming Konjin).
• Konjin's `on_encounter_ice` trigger:
    { "type": "psi_game", "params": {
        "on_mismatch": [{ "type": "redirect_encounter_to_chosen_ice", "params": { "optional": true } }],
        "on_match": []
    }}
• This is the most invasive RunStateMachine change in the Corp set — needs
  careful handling so Konjin's own subroutines still resolve after the
  redirected encounter (or are skipped if the run ended during the
  redirected encounter).

• Lockdown-aware evaluation: while `active_lockdown_card_id != ""`, the AI
  must not attempt to play a second lockdown operation
  (`no_active_lockdown` pre_play_condition already blocks it, but the
  evaluator shouldn't even consider it as a candidate play, to avoid wasted
  evaluation cycles).

• Trace evaluator: `evaluate_trace_boost(base_strength, on_success_value,
  corp_credits, estimated_runner_link)` — used by both Winchester (during
  Runner encounters) and Scapenet (on play). Should weigh: cost to
  guarantee success vs. value of on_success effect vs. credits needed for
  other turn priorities.

• Project Vacheron: the evaluator must NOT treat a Runner steal of Vacheron
  as an immediate +3 to Runner score in its win-distance calculations while
  the agenda carries 4 hosted counters; instead model it as "+0 now, +3 in
  ~4 Runner turns unless removed."

• Megaprix Qualifier: when both copies are out, the second scored copy is
  worth 4 points not 3 — evaluator's win-distance math must call
  `effective_agenda_points()` rather than printed value everywhere.

• Earth Station SEA HQ (if Corp identity): factor "Limit 1 remote server"
  into remote-server creation decisions — the AI must never attempt to open
  a second remote while on face A, and should consider flipping to face B
  once at 7+ agenda points if face B grants a win condition.

─────────────────────────────────────────────────────────────────────────────
3B. CorpTurnAI / CorpTurnAI_Tactical updates
─────────────────────────────────────────────────────────────────────────────

• Lockdown play timing: the 5 lockdown operations are each one-shot,
  turn-spanning effects. AI should sequence them for maximum value —
  e.g., play Sync Rerouting / Hyoubu Precog Manifold defensively when
  expecting a Runner rush turn; play Argus Crackdown / NAPD Cordon when
  the board has heavily-iced remotes/scoring servers.

• Cayambe Grid / La Costa Grid: AI should prioritize installing these on a
  scoring remote EARLY (before ice is built up) so the turn-begin
  advancement-placement compounds over multiple turns.

• Kakurenbo: AI should evaluate this primarily as an Archives-recursion +
  surprise-install tool — useful when Archives contains a strong asset/
  agenda/upgrade worth re-installing with a 2-advancement head start, and
  when HQ contains cards safe to discard (excess ice, redundant copies).

• Wall to Wall: AI should rez Wall to Wall ASAP (cheap rez) and prioritize
  having at least one OTHER rezzed asset on board if possible is actually
  the OPPOSITE of optimal — re-read: "if you have any OTHER rezzed assets,
  resolve 1 ... otherwise resolve up to 3" — so the FIRST Wall to Wall (with
  no other rezzed assets) gets the strong "up to 3" mode. AI should rez Wall
  to Wall before other assets when possible to capture the 3-effect mode at
  least once, OR accept the 1-effect mode as a steady-state economy engine.

• Tyr: no AI decision needed (Runner-triggered ability); CorpTurnAI should
  factor the "+1 click next turn" bonus into next-turn planning when
  Tyr has been broken via lose-click this turn.

• Vaporframe Fabricator: AI should use the click-install-from-HQ ability to
  deploy ice/assets that are otherwise too expensive to install normally
  (cost reduction = full cost), prioritizing ice for under-defended servers.

  traces only when the protected resource (program/hardware/chip/virtual)
