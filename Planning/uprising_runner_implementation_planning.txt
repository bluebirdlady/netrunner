UPRISING — RUNNER-SIDE IMPLEMENTATION PLANNING
===============================================
Date: 2026-06-10
Set: Uprising (65 entries in CSV; Runner-side subset = 30 cards)
Source: Sets/uprising.csv, Campaign/cards.json
Note: Corp-side Uprising cards (35) were completed in
Planning/uprising_corp_implementation_planning.txt (Sprints 1-6, all done).
This document covers ONLY the 30 Runner-side cards. Where a mechanic is
shared with the Corp side (e.g. trace, flip-identity), it is called out so
work isn't duplicated — the trace mechanic and flip_identity infrastructure
already exist and are reused as-is.

PHASE 1 — ENGINE INFRASTRUCTURE (GDScript changes)

─────────────────────────────────────────────────────────────────────────────
1A. EVENT-TRASH / GRIP-TRASH TRIGGERS (NEW)
─────────────────────────────────────────────────────────────────────────────
Used by: aniccam (event trashed -> draw), buffer_drive (grip/stack cards
trashed -> may rebury).

Need a generic event hook fired whenever a card is trashed "from any
location" (for Aniccam, specifically when the trashed card is type=event)
and a more specific "trashed from grip or stack" hook (for Buffer Drive).
Check whether an existing `on_card_trashed` / `runner_card_trashed` event
already exists anywhere (search AbilityInterpreter.gd for "trashed" event
dispatch) before adding a new one — likely partial infrastructure exists for
Degree Mill / Labor Rights-style effects and can be extended with a
`source_zone` / `card_type` filter rather than built from scratch.

─────────────────────────────────────────────────────────────────────────────
1B. COMPANION CREDIT-SPEND PAYMENT SOURCES (NEW)
─────────────────────────────────────────────────────────────────────────────
Used by: mystic_maemi (spend hosted credits to pay for playing events),
paladin_poemu (spend hosted credits to pay for installing non-connection
cards), mantle (spend hosted stealth credits to pay for hardware/program
costs — install costs and ability costs).

Trickster Taka already has a `runner_program_run_recurring_credits`-style
passive modifier for "spend on programs during runs" — generalize this into
a small family of "alternate payment source" passive modifiers, e.g.
`{"type": "companion_credit_source", "applies_to": "events"|"installs_non_connection"|"hardware_and_programs", "source": "self_hosted"|"stealth"}`.
The cost-resolution code path (wherever the engine currently asks "can the
Runner afford this, and where do the credits come from") needs to check
these modifiers before falling back to the credit pool. This is the central
piece of new infrastructure for this set — three cards (Mystic Maemi,
Paladin Poemu, Mantle) plus the existing stealth-spend cards (Penumbral
Toolkit, Mu Safecracker, Afterimage, Penrose) all funnel through it.

─────────────────────────────────────────────────────────────────────────────
1C. ICE-POSITION SWAP (NEW, unless already present)
─────────────────────────────────────────────────────────────────────────────
Used by: cordyceps (swap a piece of ice protecting one central server with a
piece of ice protecting another server).

Search for any existing "swap ice between servers" effect (some ice-relocate
cards may exist from other sets, e.g. Trick Shot or similar). If none, add a
`swap_ice_position` effect: takes two InstalledCard ice references, swaps
their `server_id` (and position-in-list) fields, fires any
on-server-change listeners. Keep the implementation generic (any two ice,
any two servers) even though Cordyceps restricts the choices — restriction
logic belongs in the card's effect params, not the engine primitive.

─────────────────────────────────────────────────────────────────────────────
1D. STACK "LOOK AT TOP N" / "REVEAL TOP CARD, CONDITIONAL INSTALL" (NEW)
─────────────────────────────────────────────────────────────────────────────
Used by: prognostic_q_loop (look at top 2 of stack on first run each turn;
once per turn pay 1cr to reveal top card and conditionally install at a
discount), gachapon (set aside top 6, install one at a discount, shuffle/
trash the rest), self_modifying_code (search stack for a program — likely
already supported via existing `search_deck` pattern used by Corp's
Digital Rights Management / Wave; verify and reuse).

`search_deck` (Corp side, used for Wave/Trust Operation/Gaslight/DRM) is
list-position-agnostic (search whole deck). Prognostic Q-Loop and Gachapon
need *positional* stack access (top N cards specifically, in order, with
set-aside/shuffle-back semantics). This is new — add a `stack_look_top` /
`stack_set_aside_top` family of effects operating on `ctx.runner_deck`
(or equivalent Array) by index rather than search-and-remove.

─────────────────────────────────────────────────────────────────────────────
1E. HOSTING FACEUP CARDS FOR LATER INSTALL (NEW, unless Hayley/similar exists)
─────────────────────────────────────────────────────────────────────────────
Used by: paules_cafe ([click]: host 1 program/hardware from grip faceup;
1cr: install a hosted card, first one each turn at -1cr).

Check for an existing "host card from grip, install later" pattern (some
existing console/resource may already do this, e.g. a Shaper "rig
construction" style card). If absent, add a generic `host_card_from_grip`
effect (places a CardRecord into an InstalledCard's `hosted_cards` array
without installing it) and a `install_hosted_card` effect (moves a hosted
card through normal install resolution, applying any cost modifiers from
the host).

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Per the same minimal-scope principle applied to Corp Sprint 6: most of these
30 cards are "fire and forget" passive/triggered effects that need no AI
decision beyond "play/install when affordable," which existing generic AI
heuristics already handle. Candidates for actual new AI decision points:

  - Companion spend choices (Mystic Maemi/Paladin Poemu/Mantle): when the
    Runner AI pays for an event/install/ability, it should prefer spending
    hosted companion/stealth credits over its credit pool when a
    `companion_credit_source` modifier applies (pure cost-minimization,
    likely falls out of Phase 1B's payment-resolution code automatically if
    that code always prefers alternate sources first — confirm rather than
    add bespoke AI logic).
  - Cordyceps' ice-swap target choice: needs a `choose_target`-style picker
    (reuse CorpTurnAI's `choose_target` pattern on the Runner AI side) —
    likely already has an equivalent on RunnerTurnAI; verify before adding.
  - Afterimage's sentry-bypass and Odore's conditional 0cr break: these are
    "always take if available and beneficial" — should fall out of existing
    icebreaker-use heuristics once the break/interface definitions are in
    place; no new AI code expected.
  - Gachapon / Self-Modifying Code / Simulchip / Prognostic Q-Loop: deck-
    search and heap-install choices should reuse whatever generic
    "choose best program/hardware to install from a candidate list" picker
    the Runner AI already has for similar tutors (e.g. existing Diesel/
    Quality Time-style or program-tutor cards) — confirm such a picker
    exists before writing a new one.

Recommendation: keep Phase 3 to verification (confirm existing generic
pickers handle these new cards) plus, only if testing reveals a real gap,
the single most impactful addition — most likely the companion/stealth
payment-preference check in 1B's cost-resolution path, since that's shared
infrastructure rather than a one-off.
